# Dictionary API Analysis

Analysis date: 2026-10-16

Current project decision: Merriam-Webster Learner's Dictionary API has been selected as the primary provider for the first implementation. The Free Dictionary API analysis below is retained as comparison and fallback research, not as the active integration plan.

Provider: Free Dictionary API (`dictionaryapi.dev`)

Endpoint pattern:

```text
GET https://api.dictionaryapi.dev/api/v2/entries/en/{word}
```

Sample reviewed: lookup result for `play` supplied by the user.

## Suitability

The API is suitable as a source of English vocabulary data for the academic prototype, but it must be treated as an external, fallible dependency. Meanings and phonetic text should be cached in the project's database after a successful lookup. Audio is optional and must not block vocabulary lookup or note creation.

## Response-to-CDM mapping

### Vocabulary entry

| API field | CDM target | Rule |
|---|---|---|
| `word` | `VOCABULARY_ENTRIES.word` | Normalize for lookup while retaining a display form. |
| `sourceUrls[0]` | `VOCABULARY_ENTRIES.source_url` | Current CDM has one URL although the API returns an array. Use the first nonblank URL. |
| successful import time | `VOCABULARY_ENTRIES.created_at` | Generated by the application/database, not copied from the API. |

### Phonetics

For every usable object in `phonetics[]`:

| API field | CDM target |
|---|---|
| `text` | `VOCABULARY_PHONETICS.text` |
| `audio` | `VOCABULARY_PHONETICS.audio_url` |

Both API fields may be absent or blank. `audio_url` must be nullable. Root-level `phonetic` may be used as a text fallback when no usable `phonetics[].text` is available.

Audio URL normalization rules:

- Blank value: no audio is available.
- Starts with `https://`: keep unchanged.
- Starts with `//`: prepend `https:`.
- Do not prepend another `https://` to an already absolute URL.

### Meanings

Each object in `meanings[]` contains a `partOfSpeech` and multiple `definitions[]`. Each definition becomes one `VOCABULARY_MEANINGS` record:

| API field | CDM target |
|---|---|
| `meanings[].definitions[].definition` | `VOCABULARY_MEANINGS.definition_text` |
| `meanings[].definitions[].example` | `VOCABULARY_MEANINGS.example` |
| `meanings[].partOfSpeech` | `Vocabulary_Association.part_of_speech` |

Definitions and examples require long text storage and must not be restricted to 255 characters.

### Synonyms and antonyms

Definition-level values map to `VOCABULARY_RELATED_WORDS`:

| API field | `relation_type` |
|---|---|
| `definitions[].synonyms[]` | `SYNONYM` |
| `definitions[].antonyms[]` | `ANTONYM` |

The arrays directly under a `meanings[]` object appear to aggregate related words from its definitions. Use definition-level arrays as the primary source and merge group-level arrays only as a fallback, with case-insensitive deduplication.

## Important limitation: pronunciation-to-meaning pairing

The API returns `phonetics[]` and `meanings[]` as independent arrays. It does not provide a stable identifier linking a particular pronunciation to a particular part of speech or definition.

For `play`, the sample contains one pronunciation, so the same phonetic can be associated with the noun and verb definitions without ambiguity. For a word such as `project`, multiple pronunciations may correspond to different parts of speech, but this API response shape does not reliably state that mapping.

Consequences for the intentional ternary vocabulary association:

- One usable phonetic: it may be linked to all imported senses.
- Multiple phonetics with no explicit mapping: do not create a blind Cartesian product.
- The application needs either a manual administrator confirmation step, a documented heuristic, or a different data source capable of providing pronunciation-to-sense links.

This is an API limitation, not a defect in the CDM's three-way association.

## Audio availability and reliability

The sample audio value is already a complete HTTPS URL:

```text
https://api.dictionaryapi.dev/media/pronunciations/en/play-us.mp3
```

During analysis on 2026-10-16, the documentation site was reachable, but direct checks of both the API subdomain and the audio URL timed out. The provider's public issue tracker also contains recent reports of widespread `502` and Cloudflare `522` failures. Therefore, the supplied URL format is valid, but current provider availability is unreliable.

Application behavior must be resilient:

- Display IPA text even when audio fails.
- Hide or disable the audio control when `audio_url` is blank or playback fails.
- Set request and playback timeouts.
- Never fail note creation because pronunciation audio is unavailable.
- Store the remote URL, not the audio binary, unless a separate licensed caching policy is approved later.
- Do not assume every word has audio.

## Source and license metadata

The sample includes source and license information at both entry and phonetic levels. The current CDM stores only a general entry `source_url` and phonetic `audio_url`.

Before public deployment, determine how attribution will be displayed and whether phonetic-level `sourceUrl`, license name, and license URL must be persisted. For the academic prototype, the provider/source and license can initially be documented at application level, but audio-specific attribution must not be discarded without reviewing its license terms.

## Recommended lookup flow

1. Normalize the selected word and search `VOCABULARY_ENTRIES` locally.
2. If present, return cached entry, meanings, related words, and phonetics.
3. If absent, call the external endpoint with a finite timeout.
4. Validate the response and persist usable vocabulary data transactionally.
5. If the provider fails, show a retryable lookup error; do not create partial global vocabulary data.
6. After the learner chooses a definition, copy its text into `VOCABULARY_NOTES.selected_definition` as already decided.
7. Audio playback is an optional enhancement and runs independently of saving the note.

## Pronunciation-to-sense association strategy

Never generate an unrestricted Cartesian product between every phonetic and every definition. Use the following deterministic decision process.

### Automatic cases

1. No usable phonetic:
   - Persist the entry and meanings.
   - Keep pronunciation unavailable for those senses.
   - The future PDM must permit a vocabulary sense without a phonetic reference, or postpone creation of the phonetic link.
2. Exactly one usable phonetic:
   - Associate it with every imported meaning for the entry.
3. Multiple phonetics that are explicitly tagged by the provider at entry, part-of-speech, or sense scope:
   - Use the closest available scope: sense-level first, then part-of-speech entry, then whole entry.
4. Multiple phonetics differing only by explicit regional/accent tags and known to apply to the same entry:
   - Preserve them as pronunciation variants.
   - Select one preferred accent for default playback, while keeping the alternatives.

### Ambiguous case

Treat the result as ambiguous when all of the following apply:

- More than one distinct phonetic is returned.
- More than one part of speech or pronunciation-sensitive sense exists.
- The provider supplies no field linking a phonetic to a part of speech or sense.

For an ambiguous result:

- Do not generate cross-product sense associations.
- Do not present an unverified audio file as belonging to a selected definition.
- Keep the unresolved API result transient or in a future import-staging mechanism; do not create orphaned meanings/phonetics in the final normalized vocabulary tables.
- Mark the vocabulary import as needing pronunciation review at the service/workflow level if such staging is introduced.
- Resolve it through a second provider with scoped pronunciation data or an administrator confirmation screen.

The learner may still save the selected definition text into the personal note while audio remains unavailable. The normalized `VOCABULARY_SENSES` association is created only after a pronunciation mapping is confirmed. If the physical model later permits a sense with a nullable phonetic reference, the definition may be persisted immediately and enriched with pronunciation afterward.

The confirmation screen should show definitions grouped by part of speech beside candidate IPA/audio records. The administrator selects the correct phonetic for each part-of-speech group; the backend then creates only the confirmed `VOCABULARY_SENSES` rows.

Filename guessing is not authoritative. A filename containing `noun`, `verb`, `uk`, or `us` may be used as supporting metadata only when the upstream provider explicitly documents it.

## Alternative APIs with pronunciation audio

### 1. Merriam-Webster Learner's Dictionary API — recommended primary alternative

- Free for non-commercial use up to 1,000 requests per API key per day.
- Requires an API key and provider branding/attribution compliance.
- Provides learner-oriented definitions, examples, IPA, and audio.
- Pronunciation objects can occur at entry and sense-related scopes, making pronunciation-to-meaning mapping more reliable than independent top-level arrays.
- Audio URLs are constructed from the returned audio filename using Merriam-Webster's documented media path.
- Best fit for an IELTS Academic learning project.

Potential limitation: synonyms and antonyms may require a second Merriam-Webster reference, such as its thesaurus API, and the free account is limited to two reference APIs.

### 2. Wordnik API — broad feature alternative

- Free Basic plan for nonprofit/research use with 100 calls per hour at the time of review.
- Requires an approved API key and attribution.
- Provides definitions, examples, related words, pronunciations, and audio.
- Useful when broad vocabulary coverage and related-word endpoints are important.

Potential limitation: definitions, pronunciations, and audio are exposed through separate API capabilities, so exact sense-level pronunciation pairing may still require backend reconciliation.

### 3. Wikimedia Enterprise Wiktionary API plus Wikimedia Commons — open-data alternative

- A free account includes snapshot downloads and a monthly allowance of on-demand requests.
- Wiktionary entries may contain IPA and native-speaker audio hosted on Wikimedia Commons.
- Content is openly licensed under CC BY-SA/GFDL subject to attribution and share-alike requirements.
- Suitable when open licensing, long-term data ownership, or offline ingestion is important.

Potential limitation: the API currently returns Wiktionary HTML/wikitext rather than separately parsed definition, IPA, and audio fields. Considerable parsing and normalization work is required, so this is not the simplest first integration.

### 4. `api.freedictionary.dev` — prototype-only community alternative

- Open-source, keyless API based on Wiktionary.
- Its documented word object groups `partOfSpeech`, `phonetics`, and `meanings` together, which aligns more closely with the ternary vocabulary model.
- Documented examples include direct Wikimedia or other remote audio URLs.

Potential limitation: it is a small community project with limited operational guarantees, and some documented audio links hotlink third-party providers. Use it for experimentation only after checking availability, data licensing, and third-party audio terms.

## Provider recommendation

For this project, prefer one of these two approaches:

1. Reliability-first: use Merriam-Webster Learner's Dictionary as the primary source and, if needed, one Merriam-Webster thesaurus reference for related words.
2. Zero-cost prototype: keep Dictionary API for meanings, treat audio as optional, and use manual review or a scoped fallback provider only for ambiguous multi-pronunciation words.

Do not silently combine definitions from one provider with pronunciation from another unless the backend records provenance and verifies the part-of-speech mapping.
